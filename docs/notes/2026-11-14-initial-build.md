# 最初の版を作ったときの記録（2026-11-14）

koolie の最初の版は、Claude Code に 1 日で作らせました。この文書は、そのときの AI の使い方と、その結果を数字で振り返ったものです。

数字は次の 3 つから取りました。

- Claude Code の会話ログ（本体とサブエージェント 6 体）
- git の履歴
- `koolie usage`

コストは API の定価で計算した概算で、実際の請求額ではありません。

## 進め方

1. **調査 → 設計 → 実装の順に進め、決めることは人が決めました。**
   - 設計までは plan モードで進めました。
   - 人に選んでもらったのは、言語・接続先・何で差をつけるか、の 3 点だけです。
2. **型を先に決めてから、並列で作りました。**
   - 本体のエージェント（Opus 5.5）が、共有の型と trait（model / Transport / Backend）と空の雛形を書き、先にコミットしました。
   - そのあと、独立した 4 つのモジュールを 4 体のサブエージェントに渡しました。各自が別の git worktree で作業するので、互いのビルドを壊しません。
   - その間に、本体は session / ssh / TUI / CLI を書きました。
3. **難しさに応じてモデルを使い分けました。**

   | モデル | 担当 | 理由 |
   |---|---|---|
   | Fable 5.2（high） | チャット表示、herdr-core、レビュー 2 回 | 仕様が曖昧、または深い推論が要る |
   | Opus | 使用量の集計、ホストの探索 | 比較的決まった作業 |

4. **止まっても作業を失わないようにしました。**
   - 利用上限でサブエージェントが止まったときは、SendMessage で続きから再開させました。
   - 2 回目に止まったときは、worktree に残っていた途中までの成果を本体が引き取り、テストを足して仕上げました。
5. **何段階にも分けて確かめました。**
   - 単体テスト → 偽の herdr サーバーでの結合テスト → 本物の herdr での実機確認、の順です。
   - 実機確認では、TUI を tmux の中で動かして画面を読みました（[development.md](../development.md)）。
   - 最後にレビューを 2 回しました。1 回目は全体を、2 回目は 1 回目の修正の差分を見ました。
6. **安全のための決まりを自分で課しました。** 権限の確認を省く bypass モードで動かしていたので、次のことを守りました。
   - 触るのはこのリポジトリだけにする。
   - push しない。
   - ユーザーのペインに入力しない。
   - `herdr server stop` を実行しない。

## 振り返り

### うまくいったこと

- **並列化**: 全体の 54%（約 9.9k 行）を、サブエージェントの実働 15〜20 分ずつで書けました。型を先に決めておいたので、取り込むときに作り直しは要りませんでした。
- **レビューの費用対効果**: 2 回で $12.3、見つけたのは 25 件で、1 件あたり約 $0.5 です。重大な 1 件は、ペインが閉じた瞬間にホストが「失敗」のまま止まるもので、テストでは捕まっていませんでした。
- **実機確認**: 入力欄にフォーカスがない、といった使い勝手の問題は、単体テストではまず見つかりません。tmux で画面を読む方法が役に立ちました。

### よくなかったこと

- **テストが、うまくいく場合しか見ていませんでした。** 全部のテストが通っていても、重大なバグが残っていました。
- **修正で新しいバグを入れました。** 18 件の修正のうち 3 件（約 17%）です。
- **利用上限で 2 回止まりました。** 重いエージェントを 4 体同時に動かしたので、全員が同時に上限に当たりました。
- **本体が重くなりました。** 本体だけでコストの半分以上（約 55%）を使い、キャッシュの読み込みは 1.2 億トークンでした。長い会話を抱えたまま、統合と実機確認を続けたためです。
- **cargo のビルドで待たされました。** ビルドには 1〜2 分かかり、Bash の待ち時間の上限（2 分）に当たりました。待つための回避策が増え、監視スクリプトが自分自身のプロセスに一致して終わらない失敗も 1 回ありました。

### 次にやること

1. **修正には、直す前に落ちるテストを付けます。** 修正を外してテストが落ちることを確かめる手順を、最初から入れます。
2. **並列の数を決めます。** Fable は同時に 2 体までにし、時間をずらして、Opus と混ぜます。
3. **レビューを早めます。** 最後にまとめてではなく、モジュールを取り込むたびに小さくレビューします。
4. **残っている確認をします。** SSH / tailnet 経由と herdr-core を、実機で確かめます（[status.md](../status.md)）。
